# FlowCodex 商业化就绪评估

- 评估日期：2026-10-19
- 评估对象：FlowCodex 当前代码、部署实例、运行数据与公开仓库
- 评估目标：是否可交付、是否可商业化
- 评估方法：gstack CEO/商业、工程、安全、设计、QA 视角的交叉审查
- 结论有效期：约 30 天；模型、部署和安全边界变化后需重新评估

> 说明：本报告是 AI 辅助评估，不构成法律、财务或正式安全审计意见。

## 一、结论先行

**当前项目可以交付给早期客户做“单租户、自托管、有人陪同的试点”，但还不能直接作为成熟商业产品大规模售卖，也不适合立即做多租户 SaaS。**

综合评分：**5.5 / 10**

| 维度 | 分数 | 判断 |
|---|---:|---|
| 产品价值与差异化 | 8/10 | “需求到可验证交付”的流程定位清晰，明显区别于单纯 AI Coding |
| 端到端闭环完整度 | 8/10 | 访谈、可行性、方案、编码、审查、验证、交付、知识沉淀全部跑通 |
| 实际可用性 | 7/10 | 真实 DeepSeek 运行已完成；但吞吐、错误恢复和边界情况仍需加强 |
| 安全与合规 | 4/10 | 单 Token、无 RBAC/审计、命令执行隔离不足，是商业化硬伤 |
| 运维与可靠性 | 5/10 | SQLite + 单 Worker 适合小团队，不适合 SaaS；缺迁移、监控和恢复演练 |
| UX 与上手 | 6/10 | 中文界面完整、核心路径清楚；缺设置、知识审核、搜索和引导 |

## 二、已有的强项

1. **定位清楚**：不是又一个代码补全工具，而是“需求 → 可验证交付”的工作流 Agent。
2. **流程完整**：九个阶段都有明确状态、输入、输出和门禁。
3. **质量控制前置**：需求访谈、可行性评分、方案依赖排序、范围纪律、审查和验证都已落地。
4. **隔离执行**：补丁先进入独立 worktree，审查和验证后才允许提交。
5. **知识飞轮**：前置注入、交付后蒸馏、TTL、置信度和人工反馈已实现。
6. **真实运行证据**：线上已完成一条真实 DeepSeek 运行，可行性 90/100，审查通过，验证通过，并沉淀 5 条知识资产。
7. **可部署**：Docker Compose + Caddy + 腾讯云轻量服务器部署已跑通。
8. **可维护性基础**：18 个自动化测试通过，前端/后端/部署脚本均有检查。
9. **中文产品体验**：界面、状态、错误提示和 Mock 内容均已中文化。
10. **公开仓库**：代码可见、可审计、可试用，适合早期获客。

## 三、商业化阻断项（P0）

### P0-1. 缺 License、服务条款、隐私政策和 DPA

当前公开仓库没有 `LICENSE` 文件。没有许可证意味着默认版权保留，客户不能明确获得使用、修改、分发或商业使用授权。

必须补齐：

- 商业授权协议或 EULA
- 服务条款
- 隐私政策
- 数据处理说明（DPA）
- 第三方模型数据处理披露
- 客户数据删除与导出机制

推荐路径：

- 社区版：AGPL-3.0 或 BSL 1.1
- 商业版：独立商业许可证
- 企业版：商业合同 + DPA + 安全附件

### P0-2. 单 Token，没有用户、角色和审计

当前所有操作共用一个 `API_TOKEN`，无法区分：

- 谁提交了需求
- 谁批准了方案
- 谁触发了返工
- 谁导出或提交了代码

商业化最低要求：

- 用户登录
- 角色：Owner / Maintainer / Reviewer / Viewer
- 操作审计日志
- Token 轮换与吊销
- 至少两级权限：查看与执行

### P0-3. 验证/发布命令没有真正沙箱

`verify_command` 和 `publish_command` 在应用容器内执行。虽然已经：

- 使用 `subprocess.run(list, shell=False)`
- 过滤 `API_TOKEN`、`LLM_API_KEY` 等环境变量
- 限制在隔离 worktree 中运行

但仍可访问：

- 其他项目仓库
- `data/` 中的 SQLite
- `vault/` 中的 Obsidian 笔记
- 容器网络

对单租户可信团队可以接受；对多租户或不可信仓库不可接受。

商业化方案：

- 每运行一个短生命周期沙箱容器
- 只挂载当前 worktree
- 默认禁网或白名单网络
- CPU/内存/时间/磁盘限额
- 非 root、只读根文件系统
- 明确记录命令与退出码

### P0-4. 代码和需求会发送给第三方模型

当前运行会把需求、Spec、仓库上下文、补丁和审查内容发送给 DeepSeek/OpenAI-compatible 服务。

商业化必须明确：

- 使用哪个模型供应商
- 数据是否用于训练
- 数据保留周期
- 是否支持私有化模型
- 是否支持字段/文件脱敏
- 是否支持客户自带模型 Key
- 是否支持完全离线部署

建议优先支持：

- OpenAI-compatible 私有模型
- Ollama / vLLM
- Azure OpenAI / 火山方舟 / 腾讯混元等企业通道

### P0-5. 没有成本计量、预算和配额

运行信息已经记录 `tokens_in` / `tokens_out`，但还没有：

- 单次运行成本
- 项目/用户/团队预算
- 超额告警
- 模型路由与降级
- 月度账单

真实运行样本：

```text
输入 15,966 tokens
输出 19,793 tokens
约 3 分钟完成
```

没有成本控制，商业化后很容易出现“客户用得越多，平台亏得越多”。

### P0-6. 当前架构是单租户，不是 SaaS

当前是：

- SQLite
- 单 Worker
- 单 Token
- 单容器
- 单机文件系统

适合 2-10 人自托管团队，不适合：

- 多客户隔离
- 多 Worker 并发
- 按租户计量
- 高可用
- 大规模审计

SaaS 化需要：

- Postgres
- Redis / 队列
- 租户隔离
- 对象存储
- 独立 Worker
- 计费与配额
- 监控与告警

### P0-7. 没有 GitHub/GitLab PR 集成

当前只生成隔离分支、补丁和可选本地提交，不会自动创建 PR。

商业客户通常期望：

- Push 分支
- 创建 PR/MR
- 关联需求与 Spec
- 回写审查结果
- 合并状态同步

### P0-8. 缺发布、迁移、监控和恢复体系

当前没有：

- 版本化 Release
- 数据库迁移工具
- Prometheus/OpenTelemetry 指标
- 错误追踪
- 自动备份恢复演练
- 状态页/SLA

商业化最低要求：

- 语义化版本
- 升级与回滚脚本
- 备份恢复演练
- 结构化日志
- 健康检查与告警
- 变更记录

## 四、高优先级改进（P1）

1. 知识库增加“批准/驳回”审核操作，而不只是“反馈失真”。
2. 项目设置页：编辑仓库路径、验证命令、允许路径、自动提交策略。
3. 运行列表增加搜索、状态筛选、项目筛选和分页。
4. 待补充信息/待确认方案状态增加“取消运行”按钮。
5. HTTPS 域名、CSP、HSTS、速率限制和请求体大小限制。
6. Playwright E2E 测试与 GitHub Actions CI。
7. 依赖精确锁版本，增加 `pip-audit`、Trivy、CodeQL。
8. Docker 基础镜像按 digest 固定，增加镜像扫描。
9. 备份恢复演练和版本升级演练。
10. 英文界面与国际化，决定先做中国市场还是全球市场。
11. 模型选择与预算 UI。
12. 多仓库/跨仓库策略与 GitHub PR 连接器。
13. 审计日志导出与保留策略。
14. 客户数据导出与删除流程。
15. 许可证激活、试用期和更新授权（如采用商业授权）。

## 五、产品定位建议

### 推荐定位

**“自托管的需求到可验证交付工作流 Agent”**

不是：

- 又一个 AI 代码补全
- 又一个 ChatOps 聊天机器人
- 又一个通用 Agent 平台

而是：

> 把一条需求沿着结构化 Spec、可行性门禁、方案、隔离编码、审查、验证和知识沉淀推进到可交付状态。

### 最合适的早期客户（ICP）

1. 2-10 人产品研发团队
2. 已经在用 Cursor / Claude Code / CodeBuddy，但仍被需求返工和验收困扰
3. 对代码和数据自主可控有要求，不希望把仓库交给 SaaS
4. 使用 DeepSeek 或可自建 OpenAI-compatible 模型
5. 有重复性 CRUD、前端页面、配置和 Bug 修复需求
6. 中国区团队优先，后续再扩英文市场

### 不建议的首批客户

- 资金/支付/核心安全链路
- 大型跨仓库重构
- 需要 DBA 审批的 schema 变更
- 强合规、强审计、强多租户隔离的企业

## 六、商业模式建议

### 阶段 1：早期自托管试点（现在就能做）

- 3-5 个设计伙伴
- 免费或低价试点
- 人工陪同部署和首条运行
- 收集完成率、人工介入率、单次成本和失败原因

建议价格假设：

- 试点：¥0-2,999 / 3 个月
- 早期自托管授权：¥2,999-9,999 / 年 / 实例
- 含部署支持：¥9,999-29,999 / 年

> 价格为假设，需通过 10 次客户访谈验证。

### 阶段 2：自托管 Pro / Team

- 商业 License
- 版本更新与支持
- 多用户与 RBAC
- 审计日志
- GitHub/GitLab 集成
- 私有模型支持
- 备份恢复与升级工具

建议价格假设：

- Pro：¥9,999-19,999 / 年 / 实例
- Team：¥29,999-59,999 / 年 / 10 人
- Enterprise：¥100,000+ / 年，含私有化、SSO、审计、SLA

### 阶段 3：托管 SaaS

前提：

- 多租户隔离
- Postgres + 队列
- 计费与配额
- SSO
- 安全审计
- 数据删除/导出

建议价格假设：

- Starter：¥299-599 / 月
- Team：¥1,999-4,999 / 月
- Enterprise：定制

### 不建议现在做

- 直接上多租户 SaaS
- 免费无限量
- 按 token 原价转售
- 承诺“全自动、无人值守交付”

## 九、最终建议

**当前最佳商业化路径不是立刻做 SaaS，而是：**

1. 先把产品包装成“自托管、单租户、有人陪同的早期试点”
2. 用 3-5 个真实团队验证“是否真的减少返工和等待”
3. 补齐 License、安全边界、RBAC、审计、成本和恢复能力
4. 再决定做“自托管商业版”还是“多租户 SaaS”

**一句话判断：**

> 技术和产品闭环已经成立，商业化的短板不在功能，而在信任、隔离、合规、计量和支持体系。
