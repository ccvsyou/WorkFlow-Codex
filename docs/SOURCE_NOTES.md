# 原文要点与本实现的映射

原文：[别只盯着 AI Coding，真正的变化发生在整个研发流程](https://zhuanlan.zhihu.com/p/2083953932536234138)  
作者：腾讯技术工程（知乎机构号）  
阅读日期：2026-10-19

> 说明：原文描述的是腾讯内部 OK 平台及其运营数据。本仓库是独立实现，只借鉴其公开的方法论与流程原则，不使用、不复刻其内部代码或系统。

## 原文的核心判断

1. **不要只给旧流程装 AI 插件**：真正的变化是流程结构被重新设计。
2. **人的角色从执行者变成决策者**：人负责价值判断、隐性上下文、异常干预和最终验收。
3. **信息衰减是主要断点**：用结构化 Spec 替代口头传递链。
4. **需求质量决定交付成败**：需求评审用访谈式逐层深挖，而不是机械清单。
5. **方案是质量前置卡口**：按依赖排序、垂直切片、控制粒度、插入检查点、做找茬式自审。
6. **编码要手术刀式**：简单优先、范围纪律、关键路径先测试。
7. **审查要“改善即批准”**：只把 critical 当阻塞，风格建议不阻塞；安全是硬底线。
8. **知识飞轮**：前置强注入、交付后蒸馏、TTL 老化、反馈降级。
9. **能力边界要清醒**：低复杂度、低风险、单仓库闭环先做；资金/支付/核心安全链路不自动交付。

## 原文中的公开数据

文章称，安全中心项目空间在 2026 年 4 月至 6 月共提交 254 条需求，AI 端到端完成 172 条（68%），51% 的需求在 2 小时内完成；传统模式简单需求从提出到合并中位耗时 3-5 个工作日。文章还提到知识资产累计 547 条。

这些数字来自原文，本仓库没有复现或验证其统计口径，不应把本项目的 Mock 演示结果与之等同。

## 本实现的映射

| 原文原则 | FlowCodex 实现 |
|---|---|
| 需求访谈式深挖 | `clarify` 阶段：先复述理解，再提最多 4 个问题；信息不足暂停 |
| 可行性评分 | `feasibility` 阶段：七维加权评分，默认 60 分门禁 |
| 方案按依赖排序 | `plan` 阶段：步骤含 `depends_on`、文件、验收、验证 |
| 垂直切片 | 方案步骤要求单步 ≤5 文件，完成后可验证 |
| 找茬式自审 | `plan.self_challenge` 与 unresolved_questions |
| 简单优先 | `prompts.py` 编码系统提示词中的三条纪律 |
| 范围纪律 | 方案文件清单 + `discovered_not_touched` |
| 关键路径先测试 | 编码提示词要求关键分支先写失败测试；验证命令兜底 |
| 改善即批准 | `ReviewResult` 只区分 critical / suggestion |
| 六项安全硬检查 | `prompts.py` 审查系统提示词 + `ReviewIssue.security_rule` |
| 人只做判断 | `awaiting_input`、`awaiting_plan_approval`、override、rework |
| Spec 单一事实源 | `requirements.spec_json` 注入所有下游阶段 |
| 前置强注入 | `knowledge.inject()` 按关键词/置信度选择知识 |
| 交付后蒸馏 | `distill` 阶段自动生成知识候选 |
| TTL 老化 | `knowledge.expires_at` + `expire_stale()` |
| Agent 反馈通道 | `POST /api/knowledge/{id}/feedback` 降低置信度 |
| 能力边界 | 文档中的 Non-Goals 与可行性 blockers |

## 与原 OK 平台的差异

- 原平台面向组织，本实现是单租户自托管。
- 原平台可能接入内部仓库、审批、发布系统；本实现只支持本地 git worktree 和可配置命令。
- 原平台有真实运营数据；本实现提供 Mock 模式用于验证流水线，不宣称达到相同自动交付率。
- 原平台有更完整的多角色协同；本实现先覆盖“需求提出者 + 技术决策者”两种角色。
